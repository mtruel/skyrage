# Database Migration Guide with Alembic

## Overview

This project uses **Alembic** for database schema migrations. Alembic is a lightweight database migration tool for SQLAlchemy that allows you to version control your database schema changes.

**Key Concepts:**
- **Revision**: A migration script that describes schema changes
- **Upgrade**: Apply changes to move the database forward
- **Downgrade**: Revert changes to move the database backward
- **Autogenerate**: Automatically detect schema changes by comparing SQLAlchemy models to database
- **Head**: The latest revision in the migration history

The schema in this project has been migrated from JSON-based storage to normalized relational tables for better performance and queryability.

## Schema Changes

### Before (JSON-based):
- `games.player_usernames_json`: Stored `["alice", "bob"]` as TEXT
- `rounds.player_raw_scores_json`: Stored `{"alice": 50, "bob": 30}` as TEXT

### After (Normalized):
- `game_players` table: One row per player per game with `game_id`, `username`, `player_order`
- `round_scores` table: One row per player score with `round_id`, `username`, `raw_score`

## Advanced Topics

### Branching (Multiple Migration Streams)

For larger projects with parallel development:

```bash
# Create a new branch
uv run python -m alembic revision --head=base --branch-label=feature_x -m "start feature"

# Create revision on specific branch
uv run python -m alembic revision --head=feature_x@head -m "continue feature"

# Merge branches
uv run python -m alembic merge -m "merge branches" branch1@head branch2@head

# Upgrade specific branch
uv run python -m alembic upgrade feature_x@head
```

### Conditional Autogenerate

Prevent empty migrations:

```python
# In alembic/env.py
def process_revision_directives(context, revision, directives):
    if getattr(config.cmd_opts, 'autogenerate', False):
        script = directives[0]
        if script.upgrade_ops.is_empty():
            directives[:] = []  # Don't create empty migration

# In run_migrations_online()
context.configure(
    connection=connection,
    target_metadata=target_metadata,
    process_revision_directives=process_revision_directives
)
```

### Custom Type Rendering

For custom SQLAlchemy types:

```python
# In alembic/env.py
from myapp.types import MyCustomType

def render_item(type_, obj, autogen_context):
    if type_ == "type" and isinstance(obj, MyCustomType):
        return "myapp.types.MyCustomType()"
    return False

context.configure(
    connection=connection,
    target_metadata=target_metadata,
    render_item=render_item
)
```

### Filtering What Gets Autogenerated

```python
# In alembic/env.py
def include_object(object, name, type_, reflected, compare_to):
    """Filter objects to include in autogenerate"""
    # Ignore temporary tables
    if type_ == "table" and name.startswith("temp_"):
        return False
    return True

context.configure(
    connection=connection,
    target_metadata=target_metadata,
    include_object=include_object
)
```

## Performance Improvements from Normalized Schema

### Before (JSON-based):
- **Player deletion**: O(N) - Load all games/rounds into memory, deserialize JSON
- **Finding player games**: Full table scan of all games
- **No indexes**: Can't index JSON content efficiently in SQLite

### After (Normalized):
- **Player deletion**: O(1) - SQL DELETE with foreign key indexes
- **Finding player games**: Direct JOIN query with indexes
- **Efficient queries**: Can use WHERE, GROUP BY, ORDER BY on player data

### Example Query Performance

```sql
-- Before: Requires loading all games and parsing JSON in Python
-- After: Direct SQL query with index

-- Find all games for a player
SELECT g.* FROM games g
JOIN game_players gp ON gp.game_id = g.id
WHERE gp.username = 'alice';

-- Get player statistics
SELECT 
    rs.username,
    COUNT(*) as rounds_played,
    AVG(rs.raw_score) as avg_score,
    MIN(rs.raw_score) as best_score
FROM round_scores rs
GROUP BY rs.username
ORDER BY avg_score ASC;

-- Leaderboard: Total games played per player
SELECT 
    gp.username, 
    COUNT(DISTINCT gp.game_id) as games_played
FROM game_players gp
GROUP BY gp.username
ORDER BY games_played DESC;
```

## Benefits Summary

1. **Performance**: SQL queries with indexes instead of deserializing JSON
2. **Data Integrity**: Database enforces foreign key constraints
3. **Analytics**: Can build complex queries for leaderboards, statistics
4. **Scalability**: Handles thousands of games efficiently
5. **Maintainability**: Schema changes are versioned and reviewable
6. **Future-proof**: Easy to add new features like player rankings, game history filters
7. **Team Collaboration**: Multiple developers can work on schema changes simultaneously

## Migration File Structure

A typical Alembic migration file looks like this:

```python
"""add user email column

Revision ID: ae1027a6acf
Revises: 1975ea83b712
Create Date: 2024-01-15 10:30:00.123456

"""

# revision identifiers, used by Alembic
revision = 'ae1027a6acf'
down_revision = '1975ea83b712'
branch_labels = None
depends_on = None

from alembic import op
import sqlalchemy as sa


def upgrade():
    """Apply schema changes"""
    op.add_column('users', sa.Column('email', sa.String(100)))
    op.create_index('ix_users_email', 'users', ['email'])


def downgrade():
    """Revert schema changes"""
    op.drop_index('ix_users_email', 'users')
    op.drop_column('users', 'email')
```

**Key sections:**
- **revision**: Unique identifier for this migration
- **down_revision**: Parent migration ID (forms the chain)
- **upgrade()**: Forward changes
- **downgrade()**: Reverse changes

## Common Operations in Migrations

### Table Operations
```python
from alembic import op
import sqlalchemy as sa

def upgrade():
    # Create table
    op.create_table(
        'account',
        sa.Column('id', sa.Integer, primary_key=True),
        sa.Column('name', sa.String(50), nullable=False),
        sa.Column('email', sa.String(100)),
        sa.Column('created_at', sa.DateTime, server_default=sa.func.now())
    )
    
    # Drop table
    op.drop_table('old_table')
    
    # Rename table
    op.rename_table('old_name', 'new_name')
```

### Column Operations
```python
def upgrade():
    # Add column
    op.add_column('users', sa.Column('age', sa.Integer))
    
    # Drop column
    op.drop_column('users', 'old_field')
    
    # Alter column
    op.alter_column('users', 'name', 
                    type_=sa.String(100),
                    nullable=False)
```

### Index Operations
```python
def upgrade():
    # Create index
    op.create_index('ix_users_email', 'users', ['email'])
    
    # Create unique index
    op.create_index('ix_users_username', 'users', ['username'], unique=True)
    
    # Create composite index
    op.create_index('ix_users_name', 'users', ['first_name', 'last_name'])
    
    # Drop index
    op.drop_index('ix_old_index', 'users')
```

### Constraint Operations
```python
def upgrade():
    # Add foreign key
    op.create_foreign_key(
        'fk_orders_user', 'orders', 'users',
        ['user_id'], ['id'],
        ondelete='CASCADE'
    )
    
    # Add unique constraint
    op.create_unique_constraint('uq_users_email', 'users', ['email'])
    
    # Add check constraint
    op.create_check_constraint('ck_users_age', 'users', 'age >= 18')
    
    # Drop constraint
    op.drop_constraint('fk_old', 'table_name', type_='foreignkey')
```

### Data Migrations
```python
from sqlalchemy.sql import table, column

def upgrade():
    # Define temporary table representation
    users_table = table('users',
        column('id', sa.Integer),
        column('email', sa.String)
    )
    
    # Update data
    op.execute(
        users_table.update().values(email='default@example.com')
    )
    
    # Or use raw SQL
    op.execute("UPDATE users SET status = 'active' WHERE status IS NULL")
```

def run_migrations_online():
    connectable = engine_from_config(

## Best Practices

### 1. Always Review Autogenerated Migrations

```bash
# After generating migration
uv run python -m alembic revision --autogenerate -m "add field"

# Review the file in alembic/versions/
# Check that upgrade() and downgrade() are correct
```

Autogenerate can miss:
- Renamed columns (appears as drop + add)
- Changed enum values
- Custom types
- Data migrations

### 2. Test Migrations Both Ways

```bash
# Test upgrade
uv run python -m alembic upgrade head

# Test downgrade
uv run python -m alembic downgrade -1

# Re-upgrade
uv run python -m alembic upgrade head
```

### 3. Make Migrations Idempotent

Use conditional logic when needed:

```python
from alembic import op
from sqlalchemy import inspect

def upgrade():
    conn = op.get_bind()
    inspector = inspect(conn)
    
    # Check if column exists
    if 'email' not in [c['name'] for c in inspector.get_columns('users')]:
        op.add_column('users', sa.Column('email', sa.String(100)))
```

### 4. Keep Migrations Small and Focused

- One logical change per migration
- Clear, descriptive messages
- Easier to review and revert

### 5. Write Proper Downgrade Functions

Always implement `downgrade()` to reverse changes:

```python
def upgrade():
    op.add_column('users', sa.Column('status', sa.String(20)))

def downgrade():
    op.drop_column('users', 'status')
```

### 6. Handle Data Migrations Carefully

```python
def upgrade():
    # 1. Add nullable column
    op.add_column('users', sa.Column('email', sa.String(100), nullable=True))
    
    # 2. Populate data
    op.execute("UPDATE users SET email = username || '@example.com'")
    
    # 3. Make it NOT NULL
    op.alter_column('users', 'email', nullable=False)
```

### 7. Use Version Control

- Commit migrations with code changes
- Never modify existing migrations that have been deployed
- If you need to fix a deployed migration, create a new one

### 8. Keep Track of Dependencies

For complex scenarios with multiple branches:

```python
# In migration file
depends_on = 'ae1027a6acf'  # This migration depends on another
```

## Troubleshooting

### Migration Fails

```bash
# Check current revision
uv run python -m alembic current

# View pending migrations
uv run python -m alembic history --indicate-current

# If stuck, you can manually stamp (use with caution!)
uv run python -m alembic stamp <revision_id>
```

### Database Locked Error (SQLite)

SQLite databases can have locking issues. Ensure:
- No other processes are accessing the database
- Close all DB browser tools
- Restart the app
- Check file permissions

### Autogenerate Not Detecting Changes

Common issues:
1. **Models not imported**: Ensure all models are imported in `env.py`
2. **Wrong metadata**: Check `target_metadata = Base.metadata` in `env.py`
3. **Database not up to date**: Run `uv run python -m alembic upgrade head` first

```python
# In alembic/env.py, make sure all models are imported
from db import Base  # This should import all models via Base registry
target_metadata = Base.metadata
```
